# Qué cambió respecto de OYL_Frutos_Secos_EP4_Eureka_Fix.zip

Esta edición para CMD parte del último ZIP EP4 Entrega, ya corregido para Java 21. La aplicación y los cinco JAR de Spring conservan los mismos bytes que en esa entrega. Se retiró el inicio conjunto y la apertura automática de Eureka.

Se extrajo una copia completa; no se modificó ni se sobrescribió el ZIP de partida. SHA-256 del ZIP de partida: `2091249233bbc64ffdf7d1242dde7c9dcc570b6cac01d09a206bec24f21eba5d`. El listado por archivo está en `evidencias/archivos-cambiados.tsv`. Se conservaron las pantallas y recursos de OYL, QR, avatares, inventario, animaciones, navegación y datos de retiro.

| Falla o necesidad | Archivos principales | Corrección |
|---|---|---|
| Los enlaces de las instancias no servían como demostración desde el PC | `backend/*/src/main/resources/application.properties`, `docker-compose.yml` | Cada ficha publica una URL accesible a través del Gateway; los nombres y puertos internos siguen registrados en Eureka. Existen rutas separadas de estado para Usuarios, Productos y Pedidos. |
| El enlace del panel que terminaba en /eureka/ podía dar 404 o anunciar una réplica inexistente | `RegistryRoot.java`, `RegistryRootTest.java`, `eureka-server/.../application.properties` | Las direcciones /eureka y /eureka/ llevan al panel; las consultas de descubrimiento, como /eureka/apps, conservan su ruta. Se desactivó el anuncio del propio registro como réplica. |
| El iniciador podía indicar que faltaba Java 21 aunque estaba instalado | `backend/scripts/servicios.ps1` | Lee la versión de especificación y el código de salida del proceso Java completo; busca un JDK compatible, incluido el de Android Studio. La acción `java` solo muestra versión y ruta. |
| Una compilación o un simple `/api/health` daba una impresión de arranque completo | `oyl.bat`, `scripts/servicios.ps1`, `scripts/cli/CierreConsola.java`, `estado.bat`, `stop-local.bat` | El estudiante elige cada JAR en la misma CMD y se muestran sus logs. `oyl.bat` sin argumentos solo da ayuda. Se retiró `INICIAR_OYL.bat`. La confirmación exige registro de cuatro instancias, tres rutas de salud, catálogo y puntos de retiro. La detención identifica proceso y JAR de esta copia. |
| No debía depender de Maven el día de la presentación | `backend/runtime/`, `compilar-backend.bat`, Dockerfiles | Incluye los cinco JAR y la APK ya compilados. Los Dockerfiles usan los mismos JAR. |
| El cliente nuevo no podía agregar productos aun con login remoto correcto | `LocalRepository.kt`, `CartViewModel.kt`, `LocalDao.kt` | El carrito valida la identidad y el rol de la sesión remota guardada en Room. Un cliente nuevo ya no necesita una fila en la tabla histórica de cuentas SQLite. |
| La lista inicial podía venir de semillas locales; una operación ocupada podía descartar el refresco | `OylGraph.kt`, `ProductsViewModel.kt`, `StoreDao.kt`, `CatalogScreen.kt`, `QrViewModel.kt` | La aplicación de esta entrega no inserta un catálogo de muestra en el teléfono. El catálogo completo reemplaza la copia y los cambios individuales solo actualizan su fila. La pantalla distingue actualización y caché; incluye reintento. Si el servidor contesta que un QR no existe, se respeta esa respuesta. |
| Confusión entre IP del emulador, dirección del A07 y disponibilidad de servicios | `GatewayAddress.kt`, `GatewayDialog.kt`, `OylApi.kt`, `LocalDb.kt`, pantallas de acceso y bienvenida | Permite verificar las tres rutas sin enviar un token a la dirección candidata, guardarla y usarla sin recompilar. Cada dirección conserva sus propias credenciales y su propia base local. |
| Una compra confirmada podía aparentar fallo si fallaba el refresco posterior | `CheckoutViewModel.kt`, `OrdersViewModel.kt`, `OylNavigation.kt`, `OrderController.java` | La confirmación limpia el carrito antes de refrescar el catálogo. Pedidos usa el precio confirmado por Productos al reservar, devuelve conflicto si falta stock y compensa reservas anteriores en caso de fallo controlado. El estado de pedidos se limpia al cambiar de sesión. No se garantiza ejecución exactamente una vez ante una pérdida de respuesta en la red. |
| Autenticación y roles | `TokenService.java`, `security-core/pom.xml`, `AuthViewModel.kt` | JWT estándar firmado HS256 con emisor, sujeto, rol y vencimiento. Las contraseñas se siguen validando mediante BCrypt en Usuarios. La primera ejecución del lanzador local genera una clave compartida por los servicios. |
| CRUD demostrable conservando historial | `ProductController.java`, `OylApi.kt`, `AdminProductsScreen.kt`, `ProductsViewModel.kt` | DELETE hace una baja lógica con confirmación; editar permite reactivar. El catálogo del cliente oculta inactivos. El backend valida el JWT y el rol. |
| Pruebas y firma | Suites JUnit, `GatewayEmulatorTest.kt`, `comprobar_api.py`, Gradle, Maven y `apk/` | Cobertura JaCoCo, prueba real desde Android y verificación por API. Variante de aula firmada con identificador independiente. |

Los documentos anteriores se mantienen en `documentacion/historial/` para distinguirlos de las instrucciones actuales. El backend no guarda pedidos ni cuentas de las pruebas dentro de la entrega.
